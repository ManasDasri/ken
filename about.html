# about

I build models, then try to prove them wrong.

The short version: I care more about whether a result holds than whether it looks good. The longer version is below.

  1. 01

    I started with the web and stayed for the models.

    I built web apps first: shared study rooms, a stock forecaster, dashboards. Then I started training models, and found the part I actually love: finding out whether something is true.

  2. 02

    A good-looking number is the easy part.

    With a small dataset, a model that knows nothing can still look impressive. So I split by person or by contract, tune thresholds on validation data only, and compare every score against chance.

  3. 03

    I write up the nulls too.

    Legal-BERT didn’t beat BERT. The EEG expertise result was confounded by sex. Both sit on the results pages, not buried in a footnote.

  4. 04

    I build the tools I need.

    Opening an unfamiliar repo means guessing which files matter, so I built Sprout: a Go binary on Homebrew that coding agents call over MCP. Forme, Flow and Velora are on the work page.

  5. 05

    Off the keyboard.

    Weekend animal-welfare events with Barket, ricing KDE Plasma on Linux until it looks right, and following markets and how trading systems work.

Four rules on every project.

01

Split before I look.

Train, validation and test are fixed per person or per contract and saved to disk before a model ever runs, so nothing leaks across.

02

Beat a baseline, or say so.

Every score sits next to chance and a simple baseline. If a model only matches “sex alone” or “time on task”, that is the result.

03

Report the nulls.

The predictions that failed go on the same page as the ones that held, with the same detail.

04

Ship it with tests.

90 tests pin the decisions in Clause Risk Review; Forme’s accessibility badges fail CI when the code doesn’t back them.
